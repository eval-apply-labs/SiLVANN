# SiLVANN 1.x — what each release brought

The releases of major version 1, newest first. Within a major an update keeps the models and the conversations working.
The README links here for what is new; the 0.x releases are in [`v0.md`](v0.md).

## v1.5.0

The AMD container moves to ROCm 7 and keeps the MI50. The models and the conversations of 1.4.x keep working.

**One AMD container, on ROCm 7.** `ghcr.io/eval-apply-labs/silvann:1-amd` holds ROCm 7.2.4's runtime and runs the
Instinct MI50 and MI60 and the Radeon VII, the Instinct MI100 and later, and the Radeon RX 9060 and 9070 — every such
card of a machine in the one container. 1.4.4's two AMD images are one again: the names `:1-amd-rocm6` and
`:1-amd-rocm7` stay and follow `:1-amd`, so a container made with either keeps updating, and `docker/setup.sh`'s
`update` moves it to `:1-amd`. The image with ROCm 6's runtime ended with 1.4.4.

ROCm 6.1.3, which the MI50's image held, is two years old, and a machine with a recent kernel may not take it: a
tester's Radeon VII on Fedora 44, kernel 7.2, stopped inside it as a model started. ROCm 7.2.4 is of May 2026 — not
AMD's newest, which is ROCm 10.2 and which this release does not take yet, but the newest the MI50 has been checked
on. ⚠ Whether it mends that machine is not known yet — here it ran on Ubuntu 22.04's kernel 5.15: tell us in
Discussions how it goes on yours.

**What an MI50 gets**, measured on one against 1.4.4's image: the same tokens; a prompt read as fast or 3 to 4 %
faster; an answer 2 to 5 % slower — Qwen 3.5 2B at 167 tokens a second where it gave 176, Qwen 3.6 35B-A3B with its
experts in RAM at 47.4 where it gave 48.1. The few percent are a setting of ROCm's runtime that speeds ROCm 6 up and
does nothing on ROCm 7.

**A model over several cards starts in the container.** The image holds `rocm-smi`, through which SiLVANN reads the
cards' memory; 1.4.4's AMD images did not, and a model split over two cards with tensor parallelism was refused there
(*the cards' memory cannot be read*).

**An install builds the MI50 with ROCm 7 too.** On a machine with ROCm 7 installed, `install.sh` builds the MI50's
family as it builds the newer cards'; with ROCm 6 installed it builds it as before. A machine of MI50s can move to a
current system.

**The ROCm 7 family reads a Qwen prompt faster.** It is built now with every helper inlined into its kernels, as
ROCm 6's compiler does by itself and ROCm 7's does not. On an MI50 that took a 2,000-word prompt of the Qwen 3.5 2B
from 1,460 positions a second to 1,918. The cards 1.4.4's ROCm 7 image was for — the MI100 and later, the RX 9060 and
9070 — are built the same way; not measured on them.

**Not yet run:** the image on a card other than the MI50, and an MI50 beside a newer card in one container. On
Windows nothing changes: its libraries are 1.4.4's, signed as they were.

## v1.4.4

A patch on 1.4.3, whose engine and libraries it keeps as they are: the containers. AMD's newer cards have an image,
`setup.sh` chooses the image for the cards a machine holds, and it sets SiLVANN up again on Ubuntu 22.04.

**An image for AMD's cards on ROCm 7.** `ghcr.io/eval-apply-labs/silvann:1-amd-rocm7` holds the family for the Instinct
MI100 and later (gfx908, gfx90a, gfx942, gfx950) and for the Radeon RX 9060 and 9070 (gfx1200, gfx1201), with ROCm
7.2.4's runtime. The image for the Instinct MI50 and MI60 is named `:1-amd-rocm6` now; `:1-amd`, its name through
1.4.3, stays and follows it, so a container made with that name keeps updating. ⚠ No card of its own has run in the
ROCm 7 image yet: it was built and checked on a machine of MI50s — its ROCm launched a kernel there, and a model
passed against Hugging Face on the CPU in it — and the family it holds has run on an MI355X, an RX 9070 XT and an RX
9060 XT where SiLVANN was installed, not in a container. Tell us in Discussions how it goes on yours. To build one
yourself, `docker/Dockerfile.amd-rocm7`; `docker/Dockerfile.amd` is `docker/Dockerfile.amd-rocm6`.

**`setup.sh` chooses the image for your cards.** It reads the cards the machine's driver lists: an MI50 or MI60 gets
`:1-amd-rocm6`, an MI100 or later or an RX 9060 or 9070 gets `:1-amd-rocm7`. A container takes one of the two kinds:
where a machine holds both, the newer cards, and `--card amd-rocm6` takes the MI50's instead; an update keeps the kind
its container has. The cards an image is not built for are hidden from its container, so a machine with an MI50
beside a processor's own graphics, which 1.4.3's script refused, is set up now. Where an AMD card that one of these
images runs sits beside an NVIDIA card, a new setup takes the AMD card — the order SiLVANN takes them in where it is
installed — and `--card nvidia` takes the NVIDIA card; a container that has the NVIDIA card keeps it through an update
([`docker/README.md`](../../docker/README.md#what-the-machine-needs)).

**Ubuntu 22.04's Podman.** With Podman 3 — the one Ubuntu 22.04 has — the script of the last releases started the
container, and its chat could not be reached: that Podman opens no port for a container that runs as you on the
network the companions share. A first run also ended without a word once it had made that network. On Podman 3 the
script now runs SiLVANN as the container's root — which, outside the container, is you — with none of root's
capabilities and the image's own files read-only; the files in `~/SiLVANN` stay yours, and a model answers from the
card at the rate it had. If your chat stopped answering after an update, run the script's `update` once more.
Podman 4 and later, and Docker, run as they did.

## v1.4.3

A patch on 1.4.2, whose engine and libraries it keeps as they are: the portable app has an updater and opens right the
first time, what a model makes is downloaded from the chat, and a conversation's export is saved again.

**What a model makes is downloaded from the chat.** A conversation's own folder — where the files you send it are
kept — is the model's to write in: with its `(write …)` and with the commands it runs, in a container too, where 1.4.2
let them only read it. A conversation begun with the tool is told so in its system prompt: save what you download or
generate for the user there. Each file made there shows under the answer that made it, as a chip that downloads it,
and **Account** lists it beside what you sent, marked *made by the model*; it counts in the account's space and is
exported, archived and deleted with the conversation. `(write …)` does not replace a file you sent; a command the
model runs in that folder can. A conversation begun before the update keeps the prompt it has: ask its model to save
into the conversation's folder ([`tools.md`](../tools.md#a-file-the-model-makes)).

**The portable app has an updater.** `silvann_portable_x64.zip` unzips to four folders now: `windows\`, `linux/`,
`data/` and `update\`. With SiLVANN closed, open `update\windows.exe` — on Linux run `update/linux.sh`. It says the
version the folder runs and asks before it contacts GitHub, the one site it asks; where a newer release is out it
downloads it, asks **Remove the current version?**, and puts the new one in `windows\` and `linux/`. The version you
had is deleted, or kept beside them under its number (`windows-1.4.3`). `data\` is never touched: the models, the
conversations and the accounts stay. A folder from 1.4.2 or before has no `update\`: unzip this release's zip over it
once, and from then on the updater does it ([`users.md`](../users.md#updating-the-portable-app)).

**Options says the version.** **Options → Version** shows the version SiLVANN runs. Whether a newer release is out is
asked of GitHub only when you press **check for a newer release** — nothing asks by itself, not when Options opens and
not when SiLVANN starts — and the answer names the way to it: the portable app's updater, the container's line,
`silvann update` for an install.

**The portable app's first opening on Windows.** The first time a freshly unzipped folder was opened, 1.4.1 closed by
itself, and 1.4.2 showed its window together with a tab in the browser and a box, *Press OK to close SiLVANN*.
Windows marks a program it has not run before, and Edge, started under that mark, starts itself again: the app lost
track of its own window. 1.4.3 starts Edge without the mark, and waits for a window that was handed on: one window,
the first time too.

**A conversation's export is saved again.** *Export full session* saved nothing: the download asked the server
without the page's sign-in, and every server asks for one. It asks with it now.

## v1.4.2

A patch on 1.4.1, whose engine and libraries it keeps as they are: on Windows, the setup SiLVANN chooses for a machine
stays within the card.

**On Windows, a model set up for the card stays on it.** On Linux a card refuses what it cannot hold, and the setup
SiLVANN chooses for a machine stops there. On Windows the card takes it, and what does not fit is kept in the PC's RAM
and brought to the card and back at every token: a model set up a little past the card started all the same, and
answered many times slower. On one PC (a GTX 1080 Ti) the Qwen 3.6 35B-A3B as 1.4.1 set it up answered at 0.5 tokens a
second; 1.4.2 sets it up within the card, and it answers at 11. The setup now keeps to what Windows itself budgets the
program on the card, and to what it finds on the card after each trial. Start a model again after the update and its
setup is chosen again by itself. A config that names its own `max_context` and placement is taken as it is: the
server's log says when it passes the card — set them to `"auto"` to have them chosen
([`users.md`](../users.md#on-windows)).

**Two notices on Windows.** When a page opens, the machine's admin is told if the NVIDIA driver's shared memory is on —
where to turn it off, and NVIDIA's page on it — and if the PC has no page file, or one smaller than its card. Each can
be closed for good in that browser; the server's log says the same when it starts.

**An integrated GPU beside the card is used without being asked for** (⚗ experimental). `igpu_cpu` is `"auto"` by
default: on a PC with an Intel GPU beside its NVIDIA card, the Intel GPU does what the processors would — the experts
in RAM, an older card's embedding — where the setup allows it. Windows finds the integrated GPU itself; Linux as
before, with `SILVANN_IGPU_CPU=1`. `"igpu_cpu": "no"` in a config's options keeps the processors
([`config.md`](../config.md)).

**The portable app's window, on Windows.** A new copy's first opening could end by itself a moment after it started:
Edge's process was back at once, and the app took that for its window closed. Now an Edge back within seconds is not
taken for a person closing the window: where Edge has only given the window to another of its processes the app waits
for that one, and where the window is gone it is opened again.

## v1.4.1

A patch on 1.4.0, whose engine and libraries it keeps as they are: the 📎 opens its file chooser every time.

**The 📎 opens the file chooser, every time.** A file chosen while no conversation was open or online — as none is
after an update, until you open one and send a message — was answered "Activate a conversation first", and from then on
the 📎 opened no file chooser at all until the page was loaded again. Now the chooser opens in the click itself, in the
browser. A file chosen with no conversation open starts one, as typing a message does, and a conversation that is open
and not online is brought online for it. A file larger than an attachment may be — 100 MB — is said so, where it was
refused without a word.

## v1.4.0

Your files and your space. A file you send to a chat belongs to that chat: the model reads it there, no other chat
does, and it is gone when the chat is. A shared folder holds what every chat of yours should read. **Account** shows
what your account keeps on the machine and lets you delete it, and archive a conversation to its transcript. An admin
can give each account a space. The engine and its libraries are 1.3.0's, so an update builds nothing new and Windows'
signatures are 1.3.0's; the models and the conversations of 1.3.x keep working.

**A file you send to a conversation is the conversation's own.** The 📎 takes any file now, not only documents and
pictures. It is kept as you sent it in the conversation's own folder, and the model is told its name and where it is.
That conversation's tool reads it there — `(read …)`, `(grep …)`, a command — unasked in every mode, and never writes
there. A document is still not read whole unless it is small or you ask (1.3.1): a small one's text goes in the
message, a larger one is searched; a Word document's or a PDF's text is kept beside the file for that; a file that is
not text is named to the model, which opens it where it has a command for its kind
([`tools.md`](../tools.md#a-document-you-attach)).

**Private to the chat, and gone with it.** No other conversation's model reaches a conversation's files — your own
other chats included — and no model reads a conversation's transcript or state at all. Delete the chat and its files
are deleted with it: a confidential document sent to one chat does not outlive it, and is in no other folder. Export a
conversation and its files are in the export; import it and they are back in the new conversation's own.

**A shared folder, for what every chat should read.** `attached/` in your workspace: a house style, a reference, a
dataset you come back to. Every conversation of yours reads it, as it reads the rest of your workspace. You upload to
it, make folders in it and delete from it in **Account**. A file gets from a chat to the shared folder by your own
hand — download it there, upload it here.

**Your space, in Account.** How much your account keeps on the machine and what occupies it: each conversation — its
transcript, its state (what the model holds of it, the larger part) and its own files — your workspace and the shared
folder in it. There you delete a conversation or one of its files, download a file, and upload to the shared folder
([`users.md`](../users.md#several-people-on-one-server-a-user-each)).

**Archive a conversation.** From its menu in the chat list, or in Account: its state is given up — most of the space
it takes — and its transcript and files are kept. It is still shown, saying it is archived, and no more is sent to
it. An archive is final: an archived conversation is not opened again.

**A space for each account.** An admin sets the most an account's folder may hold — in **Users**, or `silvann users
space <name> 5GB` (`none` for no limit; with no size it says what the account holds and what occupies it). Past it
the server saves no more for the account — a file sent, a picture, `(write …)`, a new conversation, a message are
refused in words that say what to do — while what the account has is still read, deleted and archived, and a
conversation's state is always put away, so nothing is lost to the limit. A shell command the model runs writes
without passing the server: it is counted when the folder is next measured.

**The conversations are closed to every model.** On a single user's machine an admin's model reaches the machine as
the tools file lets it; from this release it does not read the conversations — their transcripts, their states, the
files sent to other chats — any more than an account's that works in its own folder does. What holds it: the commands
that read files, and any command line that names a closed path, everywhere; a shell command that gets there by a path
of its own, wherever the model's commands are confined — every account that works in its own folder, and a container.
On a direct install an admin's shell commands run as your own user ([`tools.md`](../tools.md#where-the-models-commands-reach)).

**Coming from 1.3.1.** A large document sent to a chat was kept in your workspace's `attached/`, where every chat of
yours could read it; from 1.4.0 it is kept in its conversation. What 1.3.1 kept stays where it is — in what is now the
shared folder — until you delete it in Account.

**For a client of your own.** `POST /cartridges/<id>/images` takes any file and answers its `kind` — `"document"`,
`"picture"`, `"video"` or `"file"` — and `kept`, the name it is kept under; `507` where the account's space is full,
as a message and a new conversation answer then. `POST /cartridges/<id>/archive` archives a conversation; a bind, a
message or a file sent to an archived one answers `409`. `GET /account/space` says what the signed-in account holds
and its limit. A conversation in `GET /cartridges` and its description say `archived`.

## v1.3.1

A document you attach is not read whole unless it is small or you ask: a book costs the conversation the pages that
answer your question. The engine and its libraries are 1.3.0's, so an update builds nothing new and Windows'
signatures are 1.3.0's; the models and the conversations of 1.3.0 keep working.

**A large document is kept as a file, and the model looks into it.** Until now an attached document's whole text went
into the message, cut to what the conversation had room for — every page read before the answer, and what you asked
for found only where it was in the part that fit. Now a document of at most about 4,000 tokens — a few pages — goes
into the message as before, and a larger one is kept as a text file in your workspace, `attached/<its name>` (a Word
document's or a PDF's text as `<its name>.txt`). The message carries a line in its place — the file's name, where it
is, how many lines it has, how it begins — and the model's tool searches it and reads the lines it needs. Send an
encyclopedia and ask for one entry: the model looks the entry up, and the conversation grows by what it read
([`tools.md`](../tools.md#a-document-you-attach)).

**The whole, when you ask.** In the UI the attachment's chip says how the message will carry it — **in the message**,
or **kept as a file for the model to look into** — and a click on a chip kept as a file puts all of it in the message
instead, as much as the conversation has room for; another click takes that back. In words, "read all of it" has the
model read the file through. A conversation whose tool is switched off gets a document in the message, as before:
the model has no other way to reach it.

**`(grep "pattern" "file")`.** A new command of the model's tool, in the `files` skill the release ships: the lines of
a file that hold a pattern, each with its number — a regular expression, capitals and small letters alike — fifty at
once, then how to go on. With `(read "file" from count)` it is how a long file is looked into without reading it
whole: a document you attach, a log, a book. It reads as `(read …)` does — unasked in your workspace — and a subagent
has it among its read-only commands.

**For a client of your own.** `POST /cartridges/<id>/images` answers `carried` for a document — `"text"`, `"cut"` or
`"named"`: how the next message would take it — and a message's `whole` names the documents it wants in the message
whole. The kept file stays in `attached/` until you or the model remove it; the same text sent again is the same file.

## v1.3.0

v1.2.0 was a candidate and was never released: its changes are this release's.

SiLVANN asks for a sign-in everywhere, from its first run: a machine's account made where it is installed, single user
one account at a time, multi user switched in the UI with an admin's console. A sign-in ends ten minutes after its last
use, and a wrong password costs a minute. And the fixes of a review of the whole code: what the model's tools reach, a
card that refuses work, a model put down while it reads its experts. The engine changed, so its libraries are built
again and Windows' are signed again; the models and the conversations of 1.1.0 keep working.

**An account from the first run.** A machine's first account is made where SiLVANN is installed: the installer asks
for its name and password in the terminal, the container's setup does, and where neither had a terminal to ask in — the
portable app, an update — the UI's first page asks, before anything else is shown. `silvann users add <name>` makes it
from the command line. That first account is the machine's admin, and it takes what the machine held: after an update
from 1.1.0 or before, the conversations, the model's workspace, the folders it was allowed and the definitions it kept
move into `users/<name>/` the first time an account is made. Until then the chat shows only that page and the server
answers only `/health` ([`users.md`](../users.md#several-people-on-one-server-a-user-each)).

**Everyone signs in.** The UI before anything else; `silvann_cli --sign-in <name>` in a terminal, the password asked
or in `SILVANN_PASSWORD`; any other client with `POST /users/sign_in` `{"name", "password"}` and the token it answers
in `Authorization: Bearer <token>`. A sign-in is kept in the data folder, so the UI and every server on that folder
read the same one: stopping or switching the model signs no one out, and the UI asks for a sign-in with no model
running. A server that other servers use for subagents needs an account for them, named in their tools file's `agent`
entry (`account`, `password`).

**Single user: one account at a time.** A machine is single user until an admin makes it multi user. The first account
to sign in has the machine, and another account's sign-in is refused, saying who has it, until that account signs out,
its ten minutes pass, or SiLVANN is closed and opened again. The same account signs in again freely — a second
browser, the terminal chat, a script. An admin's model reaches the machine as the tools file lets it; any other
account's works in its own folder. The chat is reached from this machine alone.

**Multi user, switched in Options.** **Options → Single user or multi user**, an admin's, or `silvann users multi` and
`silvann users single` from a terminal: the model stops and SiLVANN starts again, with the same accounts and the same
folders in both. Multi user, the accounts are signed in side by side, each one's model works in its own folder, and
`silvann ui` and the portable app listen on every address: the machine's firewall decides who gets through, and
Options says the address and port to let in ([`ui.md`](../ui.md#single-user-or-multi-user)).

**An admin's console, and each user's account.** **Options** — the models, their configs, starting and stopping the
server, the tools — and **Users** are the admins'; for anyone else they are never built. In **Users** an admin adds and
removes users, makes them admins or not, and sets a password for one who does not sign in with an organisation's
account; the last admin can be neither removed nor made a user. In **Account** each user changes their own password
and signs out. The command line stays for scripts and for getting back in: `silvann users add <name> [--admin]`,
`silvann users admin <name> on|off`, `silvann users passwd <name>` for an admin who forgot theirs. A machine that had
users before this release has no admin until `silvann users admin <name> on` names one.

**A sign-in is over ten minutes after its last use.** A use is something you did: a message, a click or a key in the
page, a request of your script's. While the model answers, the sign-in is held, however long the answer and the tools
it runs take, and the ten minutes begin when the response ends — a long run of the model's goes on by itself. A page
left open keeps no one signed in: ten minutes after you last touched it, it is the sign-in page again. What a page of
your own asks by itself can say so with the header `X-Silvann-Unattended: 1`, and then does not count as a use. The
terminal chat asks for the password again when its ten minutes ran out at the prompt, and goes on with the same
conversation. Signing out, or a new password, ends a sign-in at once.

**A wrong password costs a minute.** After one, that name is refused from that address for 60 seconds — the right
password too, saying how many seconds are left (`429`, with `Retry-After`). The wait is fixed: a try made during it is
not looked at and does not lengthen it. Each wrong password is written to the system's log with the name asked for
and the address it came from — syslog's auth facility on Linux and macOS (`journalctl -t silvann`), and the server's
and the UI's own output everywhere, which is the log a container and Windows keep.

**A user's own tools.** `(add_tool …)`, where the tools file switches it on, puts what a model that works in its
account's folder adds in that folder, `users/<name>/skills_added/`: their conversations have it, no one else's do, and
it runs confined as their commands do. The machine's tools are every user's to run and no user's to change. On Windows,
where a user's commands cannot be confined, such a model runs none — `(powershell …)`, `(bash …)` and the tools it
adds; an admin's model on a single user's machine runs them ([`tools.md`](../tools.md)).

**With no sign-in to ask, the chat answers under this machine's names alone.** The page that makes the first account,
and a UI that only talks to a server on another machine, are answered when the address in the browser's bar is this
machine's — its numbers, `localhost`, its own name, the name `--host` gave — and refused otherwise, in words: a page of
another site can no longer have its own name answer `127.0.0.1` and ask them anything. A name of your own for the
machine goes in `SILVANN_HOSTS=chat.example.org`. Make the account before you open a machine to its network yourself.

**What a command the model runs is told.** It no longer gets the server's whole environment — a Hugging Face token, a
container's `-e` secrets — but what a command needs to run: where programs and libraries are, who and where it is, the
locale, the display, the cards, the certificates, the proxy. A command that leaned on another variable of the server's
gets it once the tools file's `bash` entry names it in `environment`
([`tools.md`](../tools.md#what-a-command-is-told-of-the-servers-environment)).

**`(fetch …)` reads the public internet, and nothing nearer.** A page can name any address, and a model reads what a
page tells it to. `fetch` now refuses an address of this machine or of a private network — asked of the connection
itself, each hop of a redirect included — in words that say how to allow it: the tools file's `fetch` entry lists the
hosts and addresses nearer that it may read, `"local": ["wiki.lan", "127.0.0.1"]`.

**A card that refuses work ends the turn in an error.** When a card's runtime refused to start a kernel — AMD's,
NVIDIA's or OpenCL's — the refusal was printed and the model went on over whatever the buffer held. The turn now ends
in an error that names it, and the server stays up for the next.

**An OpenCL 1.2 card whose compiler does not build the kernels is not taken.** It is refused when the model boots, and
the machine runs on the next family that takes the card or on its processors, as a card OpenCL 2.0 refuses already
did — where before the card was taken and every launch on it did nothing.

**A model put down while it reads its experts.** A server that put a model down in a living process — to draw a
picture, to lend a card — while its experts' file was still being read ahead could end with a segmentation fault. The
readers let go of the file before it is unmapped.

**A conversation on each card, after a picture.** On a server that seats a conversation on each card, the answers
after a picture in a conversation were computed at positions past their own; they are at the right ones.

**A ring of machines takes the machine named before it.** A machine's link took whoever connected first and ran what
it was sent. A ring's config now names the machine before each one, `pipeline_parallelism_prev`, and the link takes
that machine alone; a config without it works as it did, and the log says so
([`config.md`](../config.md)).

**The portable app's address.** Its UI is always at `http://127.0.0.1:8080` (`SILVANN_PORT` for another), not on a
free port chosen each time, so a bookmark and the firewall's rule keep working; a port already taken is refused in
words.

**On Windows, the page file.** A model refused by the processor's memory on Windows says that Windows needs a page
file as big as the GPU to use all of the RAM ([`users.md`](../users.md#on-windows), "The page file").

**The requirements have ceilings.** Each package whose API the code leans on — the UI's toolkit, the server's, the
Hub's client — is held below its next major version, so an install made later stays inside what its release was
tested with.

**The documents.** [`config.md`](../config.md): on a machine with no card of its own `max_context` "auto" is 32,768
positions, and a number gives more. The integrated GPU beside the card (⚗ `igpu_cpu`, `SILVANN_IGPU_CPU=1`) has run on
a laptop's Intel GPU — reported, not measured here: the 35B-A3B at 12 tokens a second with its experts there, 5 with them
on the processors; it stays experimental and off by default. [`developers.md`](../developers.md): the UI is
`silvann_ui.py` and its modules in `silvann_ui_parts/`, one concern each.

**After the update.** The first start asks for this machine's account. A script signs in and sends its token. Each
browser begins its session with the UI again, once. A `(fetch …)` of your own network's pages, and a command that read
a variable of the server's environment, need their line in the tools file, as above.

## v1.1.0

**One portable app, for Windows and Linux.** `silvann_portable_x64.zip` replaces `silvann_portable_windows_x64.zip` and
unzips to three folders: `windows\` (double-click `SiLVANN.exe`), `linux/` (run `SiLVANN.sh`, on 64-bit x86 with glibc
2.28 or later) and `data/`, the models and conversations of both. On a USB drive formatted exFAT, one folder carries

**Two REPLs that need no model.** `silvann_base_repl` boots the Eval-Apply Generalized Interpreter on the CPU in a
fraction of a second and keeps it up between forms: a form at its prompt, a file, `-e FORM`, or another program's forms
through a pipe, a line a form, as a program drives `java`. An error answers `#<error W>` and the machine is kept; a call
it cannot make stops the machine (`#<panic W>`), and `,reboot` boots a new one; Ctrl-C ends the form running, not the
machine; `,verbs` lists the verbs. `silvann_tools_repl` is the model's tool at your prompt, its commands, skills and
kept definitions over the same workspace the models use, and it asks you what a model would ask its user. `install.sh`,
`install.ps1` and both container images put the two on the PATH
([`developers.md`](../developers.md#the-interpreter-at-a-prompt), [`tools.md`](../tools.md#the-same-repl-at-your-prompt)).

**One syntax for the two Lisps.** The engine's and the tool's read one core the same: `quote`, `if`, `begin`, `let`,
`set!`, `define`, `defun`, `while`, `and`, `or`, numbers, `#t`, `#f`, `nil`, `+ - * < > = eq?`. `define` binds in the
frame it runs in, as in Scheme: at the prompt a name defined again is still one binding, and inside a `let` or a
procedure the definition goes with it. `set!` changes a name something bound and refuses one nothing did; `=` is `eq?`,
so `(= 1 1.0)` is `#f`; `+ - *` of more than two numbers work left to right in both, so a sum of floats rounds the same.
Where the two part, and why there are two: the engine's scoping is dynamic and the tool's lexical, the engine's tests
take only `#t` or `#f` and its arithmetic one kind of number at a time, and text and `lambda` are the tool's
([`two_evaluators.md`](../two_evaluators.md)).

**The engine from the tool.** `(engine '(form))` runs a form in an interpreter the tool's session keeps: the session's
values go with it, a `define` there stays for the next call, and the files' verbs are refused. A form calling what the
engine cannot call (`progn`, `lambda`, a procedure of the tool's, a list in a call's head) is refused before it goes, with the engine's word for
it, so the failure that would stop the engine stops nothing. Common Lisp's `(defun name (x) …)` is answered with the
form rewritten, in both, and `(help 'defun)` gives its shape. At the base REPL, `,tools FORM` runs a form by the tool.

**The engine.** `sys__bindings__define`, a verb of sys's: set the name where the environment holds it, add it where it
does not. `define` and `defun` lower to it, so a long session defining a name again holds one binding, not one a
definition. `add-bindings`, `remove-bindings` and `unquote` are the engine's own and refused at a prompt. The models'
programs read as before: against Hugging Face the 2B and the 35B give 1.0.3's tokens, to the same distances. An update
builds the libraries again; GitHub's Windows libraries and the portable app are signed by Eval Apply Consulting LTD.

**A mask on a release install.** A rank-1 mask (a config's `lora` naming one) did not boot on a release install, on
any model: the package that reads its file, `safetensors`, was not among the requirements. It is now, and an update
installs it. A `lora` whose folder is missing, holds neither `mask.json` nor `pack.json`, or holds a mask's
`mask.json` without its `mask.safetensors` is refused in words that say which.

**A mask beside the card's tier of experts.** On Qwen's MoE models with their experts on the CPU, a mask and the card's
tier of the experts used most were refused together — and the setup chosen at boot gives a card too small for the
model a tier, so with a mask such a model did not start unless its config named no tier. The tier now computes the
picks it holds with the mask's terms, as GLM's does: the card keeps its own copy of the mask's part for the routed
experts, about 10 MB for the 35B. On the 35B with a mask, the run with a tier gives the same top token as the run
without one at every position.

**What is loading.** A model whose experts the CPU runs loaded them after its weights on the weights' line, which
climbed from 0 to 100 a second time and read as a load going round again. The experts have a line of their own,
`loading experts: …`, in the server's log and in the UI's pane.

**The public beta, and a hardware report.** The README, [`users.md`](../users.md) and `CONTRIBUTING.md` say what the
beta is: the normal path has been tested on a reasonable sample of cards, but a bug-free experience is not expected
yet. Issues → **Hardware report** is a form for a setup the release was not tested on: the version and install, the
system, the cards and driver, the model, what you ran, the numbers and what the server printed.
